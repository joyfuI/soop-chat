# SOOP 프로토콜 관찰 근거

2026-09-09까지의 플레이어 분석과 실방송 대조 기록입니다. 표본 수·시각·빌드·반례와 미확인 범위를 보존하며, 여기에 등장하는 구현 설명은 조사 당시 상태입니다. 현재 작업은 [프로토콜 계약과 미확인 사항](../protocol.md)을 먼저 읽고, 근거를 재검토할 때 해당 절을 참고하세요. 공개 필드의 현재 계약은 [이벤트 레퍼런스](../events.md)와 소스 타입을 따릅니다.

## Node WebSocket 연결 요청 헤더 호환성

2026-09-08 전달받은 Node v26.5.1 / Undici 8.9.0 비교 실험에서는 같은 SOOP 서버에 Node 기본 WebSocket으로 연결하면 30초 timeout이 발생했고, 같은 코어에 `ws`를 주입하면 약 40ms 만에 `0001`·`0002`를 받아 입장했습니다. 헤더 이름만 바꾼 실험에서 `Sec-WebSocket-Key`는 HTTP 101을 받았지만 `sec-websocket-key`는 응답이 없었고, 다른 헤더를 하나씩 소문자로 바꾼 경우는 성공했습니다.

같은 날 Node 진입점을 `ws` 8.21.3으로 복원한 뒤 Node v26.5.1에서 공개 방송 익명 smoke test로 입장과 handshake 패킷 2개 수신을 확인했습니다. TLS 검증을 유지했고 채팅을 전송하거나 실제 메시지·인증 정보를 저장하지 않았습니다. 합성 로컬 테스트는 실제 `ws`의 헤더 표기, 바이너리 입장·수신·방송 종료 및 WebSocket 연결 요청 중 취소·timeout을 검증합니다.

## 방송 종료

2026-08-13 실방송 캡처에서 실제 방송 종료 직전에 다음 순서가 관찰됐습니다.

```text
0007 SETBJSTAT, status=0
0088 CLOSE_BROAD, payload 없음
0007 SETBJSTAT, status=0
```

공식 플레이어의 채팅 enum은 `0088`을 `SVC_CLOSE_BROAD`로 정의합니다. 스튜디오와 대시보드 팝업 채팅에서는 이를 받으면 채팅 소켓을 닫고, `PRE_BROAD_END`에서 1초 후 정상 `BROAD_END` 상태로 전환합니다. 일반 시청 플레이어의 채팅 분기는 이 opcode를 직접 처리하지 않습니다.

`soop-chat`은 `0088`을 `closeBroad`로 먼저 노출한 뒤 `ended`의 `offline` 사유를 한 번 발생시키고 소켓을 정상 종료합니다. 이는 명시적 방송 종료이므로 자동 재연결하지 않습니다.

`chatNo`는 방송인 고정값이 아니라 방송 인스턴스마다 새로 발급됩니다. 같은 방송인이 약 5분 사이 방송을 세 번 켰다 끈 캡처에서도 각 방송의 `0002 chatNo`가 `1694`, `2347`, `4253`으로 바뀌었고 매번 `0007 status=0`과 `0088`로 종료됐습니다. `0088` 이후 다음 방송에 수동으로 `connect()`하면 채널 리졸버를 다시 호출해 새 접속 정보를 사용합니다.

`0007 SVC_SETBJSTAT`은 이름 그대로 방송인 상태값을 전달하지만 최신 빌드 `202609011100`의 `LivePlayer.js`에서도 `SVC_SETCHNAME`과 같은 빈 수신 분기로 묶여 값을 읽거나 UI 명령으로 전달하지 않습니다. `LiveView.js`에도 대응 핸들러가 없습니다. 4시간 12분 캡처의 263건 중 실제 종료와 함께 온 마지막 1건을 제외한 262건이 방송인 계정의 `0004` 입장·퇴장과 거의 같은 시각에 발생했고, 실제 방송 중인 `13:16~13:32`에도 `0`과 `1`이 반복됐습니다. 추가 캡처의 두 쌍에서도 `status=0`은 방송인 표시 계정의 퇴장과 기본 ID 계정의 입장, `status=1`은 그 반대 교체와 같은 시각에 왔습니다. 7시간 12분 캡처에서는 같은 방송인의 접미사 없는 ID와 `(2)` ID가 `status=1`일 때 기본 ID 퇴장·`(2)` 입장, `status=0`일 때 `(2)` 퇴장·기본 ID 입장으로 1ms 안에 교체됐습니다. 후자의 `status=0`은 방송 시작 28초 시점이었고 방송은 이후 약 7시간 더 이어졌습니다. 다른 3시간 47분 캡처에서는 3,624건 중 3,575건이 100ms 안에 방송인 플래그 사용자의 입장과 퇴장을 모두 동반했습니다. 사용자 확인상 `status=0` 시점의 화면에는 아무 변화가 없었고, 종료 10초 전의 `status=0`도 실제 종료 신호가 아니었습니다. 실제 종료는 뒤이은 `0088`에서 발생했습니다. 따라서 영상 송출, 방송 대기, 화면 상태 또는 종료 상태로 이름 붙이지 않고 원본 숫자만 제공합니다.

같은 방송은 `17:18:13`경 영상이 방송 대기 화면으로 전환된 뒤에도 채팅 소켓이 약 10분 유지됐으며, 대기 진입을 나타내는 별도 채팅 opcode는 관찰되지 않았습니다. `17:28:11.047`에 `0007 status=0`과 `0088 closeBroad`가 수신되고 3ms 뒤 연결이 종료됐습니다. 방송 대기와 실제 종료를 구분하는 근거는 `0007`이 아니라 `0088`입니다.

방송 대기 없이 채팅창을 얼린 뒤 종료한 새 캡처에서는 `0021`과 `0019` 수신 45.7초 후 `0007 status=0`, 1ms 뒤 `0088 closeBroad`가 왔습니다. 얼음 상태 동안 일반 채팅 10건은 모두 방송인이 보냈고 별풍선·구독 선물은 계속 수신됐으므로, 얼음은 종료 전용 상태가 아니라 독립적인 채팅 권한 상태입니다. 다른 캡처에서도 얼음 뒤 일반 채팅 4건은 모두 방송인이 보냈고 도전미션 실패 알림 2건과 입장·퇴장 패킷은 계속 수신됐으며, 약 9분 뒤 `0007`과 `0088`이 같은 시각에 와서 종료됐습니다.

방송 대기와 채팅창 얼림을 모두 사용하지 않고 바로 종료한 캡처에서도 `0007 status=0` 1ms 뒤 `0088 closeBroad`가 왔습니다. 방송 대기, 채팅창 얼림, 방송 종료는 각각 독립적인 상태이며 채팅 프로토콜에서 실제 종료를 확정하는 신호는 `0088`입니다.

2026-09-08 캡처에서는 `16:25:28.507`의 `status=0` 뒤 `16:25:31.355`에 `status=1`이 왔습니다(한국 시각, 간격 2.848초). 사용자 다시보기 대조에 따르면 이 구간에서 방송인이 채팅창을 새로고침했고 영상에는 변화가 없었습니다. 수집 클라이언트의 연결도 유지됐습니다. 영상 상태와 독립적이라는 추가 근거이며, 이 한 사례로 `0007`을 새로고침 전용 신호로 정의하지 않습니다.

2026-09-08의 다른 캡처에서도 `18:57:00.981`의 `status=0`부터 `19:02:09.052`의 `status=1`까지 약 5분 8초 동안 사용자 다시보기 대조상 영상 변화가 없었습니다(한국 시각). 채팅창 조작이나 연결 상태의 원인은 확인되지 않았으므로 앞선 새로고침 사례와 같은 원인으로 단정하지 않습니다.

2026-09-08 `23:40:59.276`과 `23:41:16.367`(한국 시각)의 `status=0`은 이미 방송 대기 중이라 사용자 다시보기 대조상 영상 변화가 없었습니다. 두 패킷은 각각 같은 밀리초의 `isBJ=true` 접미사 계정 정상 퇴장과 일치했고, 두 번째에는 1ms 뒤 접미사 없는 방송인 ID가 입장했습니다. 방송인 채팅 연결의 입퇴장과 연동된다는 기존 근거를 보강하지만, 첫 번째에는 대응 입장이 없고 플레이어도 값을 무시하므로 스트리머가 특정 UI에서 채팅창을 닫았다고 단정하지 않습니다.

## 조사 당시 플레이어 채팅 opcode

빌드 `202603240400`의 채팅 enum 100개를 현재 카탈로그와 다시 대조했습니다. 기존 카탈로그에 없던 다음 opcode를 추가했습니다.

- `0088`: 방송 종료
- `0130`: 구독 세리머니 버튼
- `0131`: Savvy 알림
- `0136`: 전역 자막
- `0137`: 사용자 언어 설정
- `0138`: 꽃가루 효과
- `0139`: 라이브 자막 v2 JSON
- `0140`: 응원팀 변경
- `0141`: Nightbot 타임아웃

실방송에서 관찰된 `0110`은 이 플레이어 enum에는 없지만 실제 네트워크 근거가 있으므로 유지합니다. 당시 공개 카탈로그는 known opcode 101개와 미래 opcode용 `unknown`으로 구성됐습니다. 플레이어 번들의 자막 알림 `0115`와 UTC `0500`은 채팅 WebSocket이 아닌 별도 스트리밍 에이전트 프로토콜 상수이므로 포함하지 않습니다.

## 팬클럽 가입과 순번

팬클럽 가입은 후원 수단별로 나뉘지 않습니다. 해당 방송인에게 처음 별풍선이 귀속되면 팬클럽에 가입하며, 일반 별풍선(`0018`), 애드벌룬(`0087`), 영상풍선(`0105`)도 같은 규칙을 사용합니다. 도전미션은 도전 성공 후, 대결미션은 대결 승리 후 별풍선이 정산돼야 가입이 성립합니다.

따라서 신규 가입으로 판정된 이벤트의 `fanOrder`는 후원 수단별 순번이 아니라 해당 방송인의 공통 팬클럽 가입 순번입니다. 2026-09-02 비밀번호 방 캡처에서 `0018 fanOrder=4734` 후 59.2초 뒤 `0087 fanOrder=4735`가 수신된 것도 같은 공통 순번을 확인합니다. 도전미션 `0125`는 `fanOrder`만으로 신규 가입을 판정하지 않고 참여자의 `becameFanClubFlag`를 함께 사용합니다.

2026-09-05~06 캡처에서는 서로 다른 두 사용자의 별풍선 1개 후원에 `0018 fanOrder=293932`가 1ms 간격으로 수신됐고, 화면에도 두 사용자 모두 같은 팬클럽 가입 순번이 표시됐습니다. 이후 별풍선·애드벌룬 가입 알림 66건은 `293933`부터 `293998`까지 중복이나 건너뜀 없이 1씩 증가했습니다. 중복 직후의 애드벌룬 1개 후원 두 건도 화면에서 각각 `293933`번째·`293934`번째 팬클럽 가입으로 표시돼 후속 순번까지 대조했습니다. 이 캡처에는 중복 순번을 보정하는 알림이 없었으며, 서버 내부 가입 정보의 보정 여부나 동시 처리의 영향은 확인하지 못했습니다. 별도로 `0018 fanOrder=293871` 다음 1ms 뒤 `0087 fanOrder=293870`이 수신된 사례도 있어 순번의 유일성이나 수신 순서대로 증가함을 가정하지 않습니다. 라이브러리는 순번을 보정하거나 정렬·중복 제거하지 않고 각 이벤트를 보존합니다.

## 구독과 미션

- `0091`: 신규 구독권. chat number, receiver, sender, nickname, item type이 관찰된 레이아웃입니다. `itemType=101, tier=1`은 화면의 베이직 구독 완료와 “1개월 정기구독권” 이미지에 일치했습니다. 구독플러스 방송에서는 `itemType=201, tier=2` 3건이 플러스 구독 완료와 “1개월 정기구독권” 이미지로, `itemType=200, tier=2` 3건이 같은 완료 문구와 “구독 감사합니다” 이미지로 표시됐습니다. 이 차이는 공식 상품표의 `201 isAutoPay=false`, `200 isAutoPay=true`와 일관되지만 이미지 문구는 패킷에 없습니다. 구독 선물 수신자 30명 중 실제 선물권을 사용한 11명에게 `itemType=111, tier=1`이 왔고, 화면의 베이직 1개월 구독 완료와 일치했습니다. 별도 캡처의 `itemType=111`도 “베이직 구독하였습니다”와 왼쪽 “선물 받은 1개월 구독권” 이미지에 반복해서 일치했습니다. `itemType=101/200/201`의 화면에는 선물받았다는 표시가 없었습니다. 이전 기록의 `itemType=101/200/201 isGift=true`는 최신 공식 상품표와 달라 아래 재검증에서 `false`로 정정했습니다. 화면 관찰과 당시 저장된 상품 플래그를 구분합니다. `itemType=9200`은 공식 상품표의 `vodItemType=9200`과 화면의 “VOD에서 플러스 구독하였습니다” 문구가 일치해 `subscriptionSource="vod"`로 제공합니다. 일반 상품 번호는 `live`, 상품표에 없는 값은 `unknown`이며, `live`는 정확한 구매 화면이 아니라 비VOD 상품 번호라는 의미입니다.
- `0093`: 연속 구독 효과. `tier=1`은 화면의 “베이직”, `tier=2`는 “플러스”와 각각 대조됐습니다. 원본 `tier`와 함께 `subscriptionTier`를 `basic`/`plus`/`unknown`으로 제공합니다. 화면의 “N개월째”와 왼쪽 이미지의 “N개월 구독”은 `month`와 일치하며, `month=4`일 때 `accumulatedMonth=8`, `month=13`일 때 `accumulatedMonth=27`인 표본처럼 누적 개월은 별도 값입니다. `itemType=201/203/211/200`의 플러스 표본은 각각 화면의 25/9/11/4개월째 문구와 일치했고, `itemType=201, month=19, accumulatedMonth=23` 표본도 화면에는 “플러스 19개월째 구독 중”으로 표시됐습니다. 추가로 `itemType=100/101`의 베이직 9/12개월째, `itemType=100`의 베이직 10개월째, `itemType=101`의 베이직 2개월째, `itemType=206`의 플러스 18개월째 문구와 이미지를 대조했습니다. 새 실방송에서 `itemType=9201, tier=2, month=10, accumulatedMonth=10`도 관찰됐고 공식 상품표의 `vodItemType=9201`인 플러스 상품과 연결됐지만 화면과는 대조하지 않았습니다. 화면의 채널별 구독자 명칭은 패킷에 없으므로 합성하지 않습니다. 플레이어가 사용하는 `chatNo`, `itemType`, `senderLanguage`, `urlModify`도 구조화합니다.
- `0108`: 구독 선물권 지급. 한 사용자가 베이직 1개월 선물권을 30명에게 보낸 화면과 수신자별 30개 패킷을 대조했습니다. 추가 캡처의 선물 46건은 45명에게 각각 화면 메시지로 표시됐고, 같은 수신자에게 온 2건도 실제 별도 선물이었습니다. 이어진 `0091 itemType=111` 32건은 모두 앞선 선물 수신자와 일치했습니다. 공식 플레이어 상품표와 실방송에서 `itemType=11`은 베이직 1개월이며, `subscription_id`와 `subscription_nickname`은 구독 대상 방송인과 일치했습니다. 전체 선물 개수는 단일 `0108` 패킷에 없고 동일 내용도 실제 별도 선물일 수 있으므로 묶거나 중복 제거하지 않습니다.
- `0118`: OGQ 이모티콘 선물. 같은 발신자가 서로 다른 두 사용자에게 같은 이모티콘을 선물한 화면과 대조해 발신자·수신자·상품명·이미지 URL 필드 순서를 확인했습니다.

2026-09-05 캡처의 `0093 itemType=106, tier=1, month=12, accumulatedMonth=12`는 화면의 “베이직 12개월째 구독 중!” 문구와 일치했습니다. 기존 상품표에서 `106`은 베이직 6개월 상품이므로 `subscriptionProduct.month=6`과 화면 표시용 `month=12`를 구분합니다. 이번 화면 대조는 연속 구독 문구를 확인한 것이며 구매 기간이나 취득 경로를 추가로 확인한 것은 아닙니다.

2026-09-06 캡처의 `0108 itemType=20` 두 건은 각각 화면의 “플러스 레벨1 1개월 구독 선물권 선물”과 일치했습니다. 같은 수신자에게 각각 22.811초와 3.606초 뒤 `0091 itemType=211, tier=2`가 왔고, 화면에는 플러스 구독 완료와 “선물 받은 1개월 구독권” 이미지가 표시됐습니다. 기존 상품표는 `20`을 `level=1`, `211`을 `level=2`로 연결하지만 사용 완료 화면에는 레벨이 없었으므로 실제 레벨 변경을 뜻한다고 해석하지 않습니다. 각 이벤트의 상품 번호와 해당 메타데이터를 그대로 제공합니다.

같은 캡처의 `0093 itemType=9200, tier=2, month=3, accumulatedMonth=3`은 화면의 “플러스 3개월째 구독 중!”과 일치했고 “VOD에서”라는 표시는 없었습니다. VOD 상품 번호의 매핑은 유지하되, 신규 구독 `0091`에서 확인한 VOD 안내 문구를 연속 구독 `0093`에도 합성하지 않습니다.

`17:59:55.106`의 `0093 itemType=103, month=23, accumulatedMonth=37`은 베이직 23개월째, `18:06:33.754`의 `itemType=111, month=3, accumulatedMonth=5`는 베이직 3개월째 구독 문구와 각각 일치했습니다. 두 화면 모두 `month`를 사용했고 상품 기간이나 누적 개월을 표시하지 않았습니다. `itemType=111`의 공식 `isGift=true`도 연속 구독 문구에 선물 표시를 추가하지 않았습니다.

- `0121`: 도전미션 또는 대결미션 JSON. 공식 플레이어에서 도전미션은 `CHALLENGE_GIFT`, `CHALLENGE_NOTICE`, `CHALLENGE_SETTLE`, 대결미션은 접두사 없는 `GIFT`, `NOTICE`, `SETTLE`로 분기합니다. 이를 `missionKind`와 `action` 판별 유니온으로 노출하고 원본 객체도 보존합니다.
- 도전미션 `GIFT`는 `missionKey`, `uuid`, 후원자·방송인, chat number, relay 여부, 이미지, 제목과 후원 개수를 제공합니다. 화면의 개별 후원 문구에는 제목이 표시되지 않지만 패킷에는 들어 있습니다. `NOTICE`는 같은 `missionKey`의 제목과 `mission_status=SUCCESS|FAIL`, `SETTLE`은 제목과 `settle_count`를 전달합니다.

- 도전미션 결과는 방송인이나 도전자가 직접 선택할 수 있고, 설정한 제한 시간이 지나면 자동으로 실패합니다. 채팅 패킷의 `GIFT`·`NOTICE`·`SETTLE` payload에는 제한 시간, 결과 결정 주체, 수동·자동 여부나 실패 사유가 없으므로 패킷만으로 결과 경로를 구분하지 않습니다. 후원부터 결과까지의 관찰 시간도 프로토콜 timeout이나 `missionKey` 수명 상한으로 해석하지 않습니다.

## 채팅금지와 강퇴

`0008 setDumb`는 채팅금지 대상, 지속 시간, 누적 횟수와 명령 주체를 전달합니다. 같은 사용자가 방송인에 의해 30초·1회 채팅금지를 받은 직후 매니저에게 다시 제재돼 60초·2회로 늘어난 사례와, 방송인이 서로 다른 두 사용자에게 각각 30초·1회 채팅금지를 적용한 화면을 패킷 및 별도 확인 경로와 대조했습니다. 공식 플레이어도 지속 시간을 초 단위로 사용하며 `commanderType=1`을 방송인, `2`를 매니저로 표시합니다. 플레이어가 무시하는 다섯 번째 필드는 실제 표본에서 명령 주체의 SOOP ID와 일치해 `commanderId`로 제공합니다.

같은 최신 빌드의 `SVC_SETDUMB` 분기는 누적 횟수가 방의 최대 제재 횟수보다 작으면 UI에 `dumb` 명령을 보내고, 최대 횟수에서는 `blind` 명령으로 전환합니다. `LiveView.js`의 `dumb(t)`는 채팅창이 열려 있을 때 “대상 닉네임님이 채팅금지 N회가 되었습니다.” 행을 추가합니다. 대상이 현재 사용자이면 채팅창 상태와 별개로 명령 주체와 지속 시간을 담은 알림을 추가합니다. 두 문구 모두 수신 패킷의 메시지 본문이 아니라 플레이어가 생성하므로 다시보기에서 빠지는 현상과 모순되지 않습니다.

`0012 setUserFlag`는 공식 플레이어와 같은 순서로 변경 후·변경 전 사용자 플래그를 제공합니다. 신규 팬클럽 별풍선 후원 12건에서는 `0018 becameFanClub=true` 직후 0~10ms 안에 `0012`가 이어졌고, 주 플래그에 `32`가 추가되며 보조 플래그는 유지됐습니다. 원본 문자열과 함께 변경 전후의 전체 판정 결과를 `userStatus`와 `previousUserStatus`로 제공합니다.

새 캡처의 애드벌룬 10개와 별풍선 50개·1개 후원은 모두 팬클럽 가입 문구 뒤 열혈팬 가입 문구가 표시됐습니다. `0087 isTopFan=true`와 `0018 topFanLevel=1`이 각각 열혈팬 문구에 일치했고, 뒤따른 `0012`도 팬클럽 비트 `32` 다음 열혈팬 비트 `32768`을 추가했습니다. `0018`은 원본 `topFanLevel`과 함께 정확히 `1`일 때 `becameTopFan=true`를 제공합니다. 다른 숫자의 화면 의미는 추측하지 않습니다.

공식 플레이어는 보조 플래그의 `2^18`, `2^19`, `2^20`을 각각 `FOLLOW_TIER1`, `FOLLOW_TIER2`, `FOLLOW_TIER3`으로 정의하고 이를 `isFollower`와 `getSubscriptionTier()` 판정에 사용합니다. 새 캡처에서는 같은 사용자의 세션 두 건 모두 `2^18`이 추가돼 비구독자에서 티어 1 구독자로 바뀌었고, 약 11.2초 뒤 `0091 itemType=111` 구독 세리머니가 이어졌습니다. 라이브러리는 이를 변경 전후 `isFollower`와 `followerTier`로 제공합니다. 함께 추가된 주 플래그 `2^28`은 공식 상수에 의미가 정의돼 있지 않으므로 원본으로만 보존합니다.

플레이어 `UserInfo` getter, `LiveView.js`의 사용자 플래그 판정과 공식 Chat SDK의 `userStatus`를 대조해, 원본 사용자 플래그가 있는 이벤트에는 공통 `UserStatus`를 제공합니다. BJ·매니저·열혈팬·팬·서포터·귓속말 수신 허용·구독자·게스트·퀵뷰·모바일·성별·A태그·운영 권한 비트를 각각 독립적으로 판정하며, 여러 비트를 하나의 역할이나 UI 표시 등급으로 축약하지 않습니다. 이벤트별 필드명과 전체 비트 표는 [이벤트 레퍼런스](../events.md#사용자-상태)에 정리합니다.

## 매니저 상태와 안내

2026-09-08 `14:19:39.313`(한국 시각)의 `0004` 입장에서 `isFixedManager=true, isManager=false`였던 사용자에게 같은 시각 `0013 hide=0`이 수신됐습니다. 변경 전후 `flag1`의 차이는 매니저 비트 `256`뿐이고 `flag2`는 같았습니다. 이후 채팅 4건에서 두 매니저 비트가 유지됐으며, `14:42:28.891`의 채팅 발신자와 `0013` 대상의 ID·닉네임이 일치하고 다시보기 화면에 매니저 배지가 표시된 것을 사용자와 대조했습니다. 실제 ID·닉네임은 기록하지 않습니다. 해당 입장 시점의 지정 안내는 다시보기에서 확인하지 못했습니다.

당일 공식 플레이어 HTML에서 최신 참조 빌드 `202609011100`을 확인하고 다음 경로를 추적했습니다.

- [LivePlayer.js](https://static.sooplive.com/asset/app/liveplayer/player/dist/LivePlayer.js?_=202609011100)의 `SVC_SETSUBBJ` 수신 분기는 `[userId, userFlag, hide, nickname]`을 읽습니다. 사용자 목록을 갱신한 뒤 매니저 비트 판정을 `status`, 세 번째 필드의 숫자 변환 결과를 `hide`로 담아 UI의 `manager` 명령으로 전달합니다.
- [LiveView.js](https://static.sooplive.com/asset/app/liveplayer/view/dist/LiveView.js?_=202609011100)의 `manager(t)`는 사용자 목록·본인 권한을 먼저 갱신하고, `isViewJoinMsg()`와 `isChatOpen()`이 모두 참일 때 안내를 출력합니다. 매니저 모델(모듈 `113`)의 `isViewJoinMsg()`는 `hide`가 `1`이 아닌지만 검사하며, 일반 입퇴장 표시 옵션을 읽지 않습니다. `isChatOpen()`은 플레이어의 `chat_open` 클래스를 검사합니다.
- 같은 모델의 `isSetManager()`는 전달된 `status`를 검사해 지정·해임 문구를 선택합니다. 본인이 매니저로 지정된 경우 채팅 안보기 초기화 안내가 추가될 수 있습니다. 안내는 UI가 생성하며 채팅 패킷 본문에 들어 있는 메시지가 아닙니다.

따라서 이번 `hide=0, isManager=true` 표본은 공식 라이브 플레이어에서 채팅창이 열려 있으면 지정 안내의 출력 조건을 충족합니다. 실제 당시 출력 여부와 다시보기에 남지 않는 이유는 이 코드 조사로 확정하지 않습니다. 라이브러리의 `hidden`은 모든 0 아닌 값을 숨김으로 취급하던 기존 구현에서 `hide === 1`로 바로잡았습니다. `2`·`-1`은 실제 수신 표본이 아니라 공식 비교 조건을 검증하는 합성 테스트 값이며 원본 `hide`는 유지합니다. 이벤트 provenance는 상태·배지 대조를 근거로 `observed`로 올리되 안내 조건은 플레이어 근거로 구분합니다.

2026-09-08 추가 캡처의 `22:52:02.041` 표본은 `hide=0, isManager=true, isFixedManager=false`였고, 직전 같은 사용자의 채팅에는 두 매니저 비트가 모두 없었습니다. 대상 닉네임은 사용자가 제시한 정보와 UTF-8 바이트 단위로 일치했고, 사용자는 이 시점에 실제로 매니저가 된 사실을 확인했습니다. 같은 캡처에서 입장 직후 수신된 고정 매니저 표본 다섯 건도 모두 `hide=0, isManager=true, isFixedManager=true`였으며, 그중 한 사용자는 뒤이은 채팅에서 두 비트와 매니저 배지가 확인됐습니다. 실제 ID·닉네임은 기록하지 않습니다.

공식 `manager(t)`와 매니저 모델은 `isFixedManager`를 안내 조건으로 검사하지 않습니다. 따라서 위 일반 매니저 지정과 고정 매니저 입장은 모두 채팅창이 열려 있을 때 같은 “대상 닉네임님이 매니저가 되셨습니다.” 행을 생성합니다. 이 행은 `0013`을 받아 플레이어가 만든 시스템 UI이므로 다시보기 채팅에 남지 않을 수 있으며, 캡처 시점의 실제 행 출력은 다시보기만으로 재확인할 수 없습니다.

## 인증 연결

### 로그인과 19금 방

성인 인증이 완료된 한 계정으로 이미 19금으로 설정된 서로 다른 두 실방송을 확인했습니다. 익명 라이브 정보 API는 두 방 모두 `RESULT=-6`만 반환하고 `REASON`은 없었지만, 로그인 뒤에는 `RESULT=1`과 채팅 서버 정보가 반환됐고 두 방 모두 실제 `0002` 입장 응답까지 받았습니다. 실제 계정 정보와 방송인 아이디는 기록하지 않습니다.

확인된 최소 순서는 다음과 같습니다.

1. `LoginAction.php`에 계정 정보를 전송하고 로그인 유지·아이디 저장 없이 `AuthTicket`을 받습니다.
2. 라이브 정보 API에 `AuthTicket` 쿠키를 보내 `TK`, `FTK`와 일반 `ChannelInfo` 필드를 받습니다.
3. `0001`에 `TK`를 넣은 `\f<TK>\f\f16\f`을 전송합니다.
4. 서버의 `0001` 뒤 `0002`에 `CHATNO`와 `FTK`를 넣은 `\f<CHATNO>\f<FTK>\f0\f\f\f`을 전송합니다.

공식 플레이어는 `0002`의 마지막 필드에 접속 로그와 `pwd`, `auth_info`, `pver`, `access_system` 값을 조합하지만, 두 실방송의 읽기 전용 입장에는 빈 값으로 충분했습니다. 라이브러리는 확인된 최소 필드만 보냅니다.

`createNodeChannelResolver`는 계정 정보를 받아 첫 인증에서 얻은 `AuthTicket`을 resolver closure가 살아 있는 동안 Node 프로세스 메모리에서 재사용합니다. `TK`와 `FTK`도 `ChannelInfo`의 열거 필드나 이벤트에 넣지 않고 내부 `WeakMap`에 연결하므로 JSON 직렬화로 유출되지 않습니다.

현재 구현은 `AuthTicket`의 만료 시간을 알지 못하며 자동 갱신이나 인증 실패 후 재로그인을 시도하지 않습니다. 서버에서 티켓이 만료되거나 무효화되면 이후 라이브 정보 조회 오류가 호출자에게 전달됩니다. 장시간 실행 서비스는 이 상황을 애플리케이션 인증 수명주기로 처리해 resolver 또는 `SoopChat` 인스턴스를 새로 만들어야 합니다. 정확한 TTL과 무효화 응답 형태가 실증되지 않았으므로 추측에 기반한 refresh 로직은 추가하지 않습니다.

서버 보조 브라우저 연결에서는 `authenticateNode`가 서버에 보관할 `AuthTicket`을 반환하고, `resolveNodeChannel`의 두 번째 인수에 이를 `authentication`으로 전달합니다. 이 호출은 직렬화 가능한 `AuthenticatedChannelInfo`에 `TK`와 `FTK`를 포함합니다. 브라우저 클라이언트는 두 값을 검증하고 내부 `WeakMap`으로 옮긴 뒤 위와 같은 인증 패킷을 보냅니다. `AuthTicket`은 브라우저에 전달하지 않습니다. 애플리케이션 서버를 무상태로 운영하려면 `AuthTicket`만 인증된 암호화 방식으로 봉인한 HttpOnly 쿠키를 사용하며, 계정 비밀번호나 평문·서명 전용 토큰은 쿠키에 저장하지 않습니다. 로그인 API 오류는 계정 정보나 응답 본문을 포함하지 않는 `AuthenticationError`로 전달합니다.

서로 다른 두 실방송에서 방송 중 19금이 적용된 것을 확인했습니다. 두 캡처 모두 전용 채팅 opcode나 소켓 재연결이 없었고, 이미 연결된 익명 채팅 WebSocket은 방송 종료까지 유지됐습니다. 두 번째 방송은 카테고리 변경과 함께 19금을 적용했지만 `0053 setBroadInfo`도 수신되지 않았습니다. 입장·퇴장 변화는 접근 제한의 직접 신호가 아니므로 이벤트로 해석하지 않습니다. 현재 채널 리졸버는 최초 연결과 재연결 때만 제한을 판정하며, 연결 중 제한 변경을 감지하려면 별도의 라이브 정보 조회가 필요합니다.

시작부터 끝까지 19금이었던 추가 방송에서는 첫 연결 시도가 `RestrictedRoomError("adult")`로 끝난 뒤 18.9초 후 인증 연결이 성공해 약 2시간 30분 동안 유지됐습니다. 비방송인 입장과 채팅에는 `followerTier=0/1/2`가 모두 있었고 전용 opcode나 패킷 플래그는 없었습니다. 따라서 `followerTier`는 19금 제한의 신호가 아니며, 제한은 WebSocket 연결 전 라이브 정보 조회 결과로 판정합니다.

### 비밀번호 방

비밀번호 보호 방송 인증 경로는 조사 당시 별도로 사용한 2026-09-01 플레이어 번들 `202609011100`과 실제 비밀번호 방송에서 다음 순서를 확인했습니다.

1. 일반 라이브 정보 요청의 `pwd`에 방 비밀번호를 보내 채널 정보와 `BPWD=Y`를 받습니다. 이 응답의 `RESULT=1`만으로는 비밀번호 정답 여부를 판정할 수 없습니다.
2. 반환된 `BNO`로 같은 API를 `type=aid`, `bno`, `pwd`와 함께 다시 요청합니다. 정답은 `RESULT=1`과 스트림 식별자를, 오답은 `RESULT=0`을 반환했습니다. 라이브러리는 이 단계에서 오답을 `RestrictedRoomError`의 `password` 사유로 분류합니다.
3. 익명 채팅은 기존 `0001` 뒤 `0002`의 추가 정보 필드에 플레이어 형식의 `log`, `pwd`, 빈 `auth_info`, `pver=2`, `access_system=html5` 요소를 보냅니다. 실제 채팅방의 `0002` 입장 응답까지 확인했습니다.

로그인 계정이 함께 있으면 두 라이브 정보 요청에 기존 `AuthTicket` 쿠키를 보내고, 기존처럼 `0001`의 `TK`와 `0002`의 `FTK`에 비밀번호 추가 정보 필드를 함께 사용합니다. 방 비밀번호는 계정 로그인과 독립적이며 `roomPassword`로 전달합니다. 비밀번호와 계정 정보, 반환된 인증 값 및 실제 방송인 아이디는 기록하지 않습니다.

### 구독플러스 방

구독플러스 미가입 상태의 익명 라이브 정보 요청은 `RESULT=-14`, 빈 `REASON`, `P_MIN_TIER=2`, `TIER_TYPE=0`을 반환하고 채팅 서버 정보는 제공하지 않았습니다. 라이브러리는 이 결과를 `RestrictedRoomError`의 `subscriptionPlus` 사유로 분류합니다.

같은 방송에 구독플러스 권한이 있는 계정의 `AuthTicket`을 보내면 `RESULT=1`과 `TK`·`FTK`를 반환했고, 기존 인증 연결의 최소 `0001`·`0002` 패킷만으로 실제 채팅 입장 응답을 받았습니다. 따라서 Node의 `credentials`와 서버 보조 브라우저의 인증 채널 정보 흐름을 그대로 사용합니다. 계정과 방송인 아이디는 기록하지 않습니다.

13시간 5분의 실제 구독플러스 방송에서 수집 계정의 `0002 userStatus.followerTier`는 2였고, 일반 채팅 31,715건의 발신자 155명도 모두 티어 2였습니다. `0004` 입장 사용자 1,362건 중 1,358건은 티어 2였고 나머지 4건은 티어 0인 방송인이었습니다. 19금과 구독플러스가 함께 적용된 추가 2시간 35분 방송에서도 비방송인의 일반·OGQ 채팅 10,396건(88명)과 입장 257건(128명)은 모두 티어 2였고, 티어 0은 방송인뿐이었습니다. 직전 19금 전용 방송에는 비방송인 티어 0·1·2가 모두 있었으므로 이 차이는 19금이 아니라 구독플러스 참여 제한과 일치합니다. 구독플러스 방 전용 채팅 opcode는 없었으며, 같은 방송의 `0087 adconEffect` 두 건도 `isSubRoom=false`였으므로 이 필드는 구독플러스 제한 여부가 아닙니다.
