# SOOP 채팅 프로토콜 조사 노트

이 문서는 공개 방송의 익명 채팅과 Node 및 서버 보조 브라우저의 인증된 19금 채팅 읽기에 필요한 사실, 아직 구현하지 않은 기능의 후속 조사 지점을 기록합니다. SOOP의 공개 사양이 아니라 2026-08-27까지의 플레이어 분석 및 실방송 관찰 결과입니다. 라이브러리가 공개하는 이벤트와 `data` 필드는 [이벤트 레퍼런스](events.md)를 참고하세요.

## 근거

- 현재 플레이어: `LivePlayer.js`와 `LiveView.js` 빌드 `202603240400`
- 보조 스크립트: `als.js` 빌드 `202310271100`
- TypeScript 참고: `reindeer002/soop` 커밋 `ec0ef735bc5aa2b8eaa572c6495a64956f5016f0`
- Java 참고: `getCurrentThread/soopapi` 커밋 `fc805ac42051e495c439f88eff3a33cc02eac8c5`

플레이어와 실방송 캡처를 우선하며, 참고 라이브러리에서만 확인한 이벤트는 `EVENT_CATALOG`에서 `reference`로 표시합니다.

## 공개 방송 연결

Node 진입점은 다음 API를 POST로 호출합니다.

```text
https://live.sooplive.com/afreeca/player_live_api.php?bjid=<streamerId>
```

요청에는 `bid`, `type=live`, `player_type=html5`, `stream_type=common`, `quality=HD`, `mode=landing` 등이 포함됩니다. 응답의 `BNO`, `CHATNO`, `CHDOMAIN`, `CHPT`를 검증하고 아래 WebSocket을 엽니다.

```text
wss://<CHDOMAIN>:<CHPT + 1>/Websocket/<streamerId>
Sec-WebSocket-Protocol: chat
```

브라우저에서는 라이브 API가 `Access-Control-Allow-Origin: https://play.sooplive.com`으로 제한되어 있으므로 임의 웹사이트가 직접 호출할 수 없습니다. WebSocket 자체는 다른 Origin에서도 upgrade되지만, 접속 정보를 얻으려면 애플리케이션 서버의 리졸버가 필요합니다.

TLS 검증은 절대 비활성화하지 않습니다. 인증서 문제가 발생하면 환경의 CA 설정을 고치거나 오류를 호출자에게 전달합니다.

## 프레이밍과 입장

헤더는 14바이트입니다.

```text
ESC TAB | opcode 4 bytes | payload length 6 bytes | flags 2 bytes | UTF-8 payload
```

payload 길이는 UTF-8 바이트 수입니다. 필드는 form feed(`0x0c`)로 구분됩니다.

익명 클라이언트는 다음 순서로 입장합니다.

1. `0001` payload `\f\f\f16\f`
2. 서버의 `0001` 응답 대기
3. `0002` payload `\f<CHATNO>\f\f\f\f\f`
4. 서버의 `0002` 응답 후 연결 완료
5. 60초마다 `0000` keepalive

WebSocket 메시지 경계와 SOOP 패킷 경계가 같다고 가정하지 않습니다. 구현은 분할 패킷과 결합 패킷을 모두 처리합니다.

## 방송 종료

2026-08-13 실방송 캡처에서 실제 방송 종료 직전에 다음 순서가 관찰됐습니다.

```text
0007 SETBJSTAT, status=0
0088 CLOSE_BROAD, payload 없음
0007 SETBJSTAT, status=0
```

공식 플레이어의 채팅 enum은 `0088`을 `SVC_CLOSE_BROAD`로 정의합니다. 스튜디오와 대시보드 팝업 채팅에서는 이를 받으면 채팅 소켓을 닫고, `PRE_BROAD_END`에서 1초 후 정상 `BROAD_END` 상태로 전환합니다. 일반 시청 플레이어의 채팅 분기는 이 opcode를 직접 처리하지 않습니다.

`soop-chat`은 `0088`을 `closeBroad`로 먼저 노출한 뒤 `ended`의 `offline` 사유를 한 번 발생시키고 소켓을 정상 종료합니다. 이는 명시적 방송 종료이므로 자동 재연결하지 않습니다.

`chatNo`는 방송인 고정값이 아니라 방송 인스턴스마다 새로 발급됩니다. 같은 방송인이 약 5분 사이 방송을 세 번 켰다 끈 캡처에서도 각 방송의 `0002 chatNo`가 `1694`, `2347`, `4253`으로 바뀌었고 매번 `0007 status=0`과 `0088`로 종료됐습니다. `0088` 이후 다음 방송에 수동으로 `connect()`하면 채널 리졸버를 다시 호출해 새 접속 정보를 사용합니다.

`0007 SVC_SETBJSTAT`은 이름 그대로 방송인 상태값을 전달하지만 현재 플레이어는 이 값을 해석하지 않습니다. 4시간 12분 캡처의 263건 중 실제 종료와 함께 온 마지막 1건을 제외한 262건이 방송인 계정의 `0004` 입장·퇴장과 거의 같은 시각에 발생했고, 실제 방송 중인 `13:16~13:32`에도 `0`과 `1`이 반복됐습니다. 추가 캡처의 두 쌍에서도 `status=0`은 방송인 표시 계정의 퇴장과 기본 ID 계정의 입장, `status=1`은 그 반대 교체와 같은 시각에 왔습니다. 사용자 확인상 `status=0` 시점의 화면에는 아무 변화가 없었고, 종료 10초 전의 `status=0`도 실제 종료 신호가 아니었습니다. 실제 종료는 뒤이은 `0088`에서 발생했습니다. 따라서 영상 송출, 방송 대기, 화면 상태 또는 종료 상태로 이름 붙이지 않고 원본 숫자만 제공합니다.

같은 방송은 `17:18:13`경 영상이 방송 대기 화면으로 전환된 뒤에도 채팅 소켓이 약 10분 유지됐으며, 대기 진입을 나타내는 별도 채팅 opcode는 관찰되지 않았습니다. `17:28:11.047`에 `0007 status=0`과 `0088 closeBroad`가 수신되고 3ms 뒤 연결이 종료됐습니다. 방송 대기와 실제 종료를 구분하는 근거는 `0007`이 아니라 `0088`입니다.

방송 대기 없이 채팅창을 얼린 뒤 종료한 새 캡처에서는 `0021`과 `0019` 수신 45.7초 후 `0007 status=0`, 1ms 뒤 `0088 closeBroad`가 왔습니다. 얼음 상태 동안 일반 채팅 10건은 모두 방송인이 보냈고 별풍선·구독 선물은 계속 수신됐으므로, 얼음은 종료 전용 상태가 아니라 독립적인 채팅 권한 상태입니다. 다른 캡처에서도 얼음 뒤 일반 채팅 4건은 모두 방송인이 보냈고 도전미션 실패 알림 2건과 입장·퇴장 패킷은 계속 수신됐으며, 약 9분 뒤 `0007`과 `0088`이 같은 시각에 와서 종료됐습니다.

방송 대기와 채팅창 얼림을 모두 사용하지 않고 바로 종료한 캡처에서도 `0007 status=0` 1ms 뒤 `0088 closeBroad`가 왔습니다. 방송 대기, 채팅창 얼림, 방송 종료는 각각 독립적인 상태이며 채팅 프로토콜에서 실제 종료를 확정하는 신호는 `0088`입니다.

## 현재 플레이어 채팅 opcode

빌드 `202603240400`의 채팅 enum 100개를 현재 카탈로그와 다시 대조했습니다. 기존 카탈로그에 없던 다음 opcode를 추가했습니다.

- `0088`: 방송 종료
- `0130`: 구독 세리머니 버튼
- `0131`: Savvy 알림
- `0136`: 전역 자막
- `0137`: 사용자 언어 설정
- `0138`: 꽃가루 효과
- `0139`: 라이브 자막 v2 JSON
- `0140`: 응원팀 변경
- `0141`: Nightbot 타임아웃

실방송에서 관찰된 `0110`은 이 플레이어 enum에는 없지만 실제 네트워크 근거가 있으므로 유지합니다. 따라서 공개 카탈로그는 known opcode 101개와 미래 opcode용 `unknown`으로 구성됩니다. 플레이어 번들의 자막 알림 `0115`와 UTC `0500`은 채팅 WebSocket이 아닌 별도 스트리밍 에이전트 프로토콜 상수이므로 포함하지 않습니다.

## 구독과 미션

- `0091`: 신규 구독권. chat number, receiver, sender, nickname, item type이 관찰된 레이아웃입니다. `itemType=101, tier=1`은 화면의 베이직 구독 완료와 “1개월 정기구독권” 이미지에 일치했습니다. 구독 선물 수신자 30명 중 실제 선물권을 사용한 11명에게 `itemType=111, tier=1`이 왔고, 화면의 베이직 1개월 구독 완료와 일치했습니다. 별도 캡처의 `itemType=111`도 “베이직 구독하였습니다”와 왼쪽 “선물 받은 1개월 구독권” 이미지에 반복해서 일치했습니다. 공식 상품표에서 `itemType=101`의 `isGift`가 `true`여도 화면에는 선물받았다는 표시가 없었으므로, 이 값은 현재 이벤트의 취득 경로로 확대 해석하지 않습니다. `itemType=9200`은 공식 상품표의 `vodItemType=9200`과 화면의 “VOD에서 플러스 구독하였습니다” 문구가 일치해 `subscriptionSource="vod"`로 제공합니다. 일반 상품 번호는 `live`, 상품표에 없는 값은 `unknown`이며, `live`는 정확한 구매 화면이 아니라 비VOD 상품 번호라는 의미입니다.
- `0093`: 연속 구독 효과. `tier=1`은 화면의 “베이직”, `tier=2`는 “플러스”와 각각 대조됐습니다. 원본 `tier`와 함께 `subscriptionTier`를 `basic`/`plus`/`unknown`으로 제공합니다. 화면의 “N개월째”와 왼쪽 이미지의 “N개월 구독”은 `month`와 일치하며, `month=4`일 때 `accumulatedMonth=8`, `month=13`일 때 `accumulatedMonth=27`인 표본처럼 누적 개월은 별도 값입니다. `itemType=201, month=19, accumulatedMonth=23` 표본도 화면에는 “플러스 19개월째 구독 중”으로 표시됐습니다. 추가로 `itemType=100/101`의 베이직 9/12개월째, `itemType=100`의 베이직 10개월째, `itemType=101`의 베이직 2개월째, `itemType=206`의 플러스 18개월째 문구와 이미지를 대조했습니다. 화면의 채널별 구독자 명칭은 패킷에 없으므로 합성하지 않습니다. 플레이어가 사용하는 `chatNo`, `itemType`, `senderLanguage`, `urlModify`도 구조화합니다.
- `0108`: 구독 선물권 지급. 한 사용자가 베이직 1개월 선물권을 30명에게 보낸 화면과 수신자별 30개 패킷을 대조했습니다. 공식 플레이어 상품표와 실방송에서 `itemType=11`은 베이직 1개월이며, `subscription_id`와 `subscription_nickname`은 구독 대상 방송인과 일치했습니다. 전체 선물 개수는 단일 패킷에 없으므로 합성하지 않습니다.
- `0118`: OGQ 이모티콘 선물. 같은 발신자가 서로 다른 두 사용자에게 같은 이모티콘을 선물한 화면과 대조해 발신자·수신자·상품명·이미지 URL 필드 순서를 확인했습니다.

`LiveView.js`의 내부 상품표 57개 행을 `subscriptionProduct`로 연결합니다. 공식 UI에서 `0091`은 원본 값이 `itemType` 또는 `vodItemType`과 처음 일치하는 행을 사용하고, `0108`은 `itemType`이 일치하는 선물 행만 사용합니다. `0093`도 같은 상품표의 첫 일치 규칙으로 부가 정보를 제공합니다. 따라서 중복된 구형 `itemType=1/2/3`은 단일 패킷만으로 유일하게 구분하지 못하며 공식 표 순서의 첫 행을 반환합니다.

| 티어·레벨 | 일반 선물 1/3/6개월 | 세리머니 선물 일반/체험 | 일반 구독 | 자동 결제 선물 |
|---|---|---|---|---|
| 베이직 | `101` / `103` / `106` | `11` / `12` | `111` | `100` |
| 플러스 1 | `210` / `213` / `216` | `20` / `30` | `1111`, `2013` | `310` |
| 플러스 2 | `201` / `203` / `206` | `21` / `31` | `211` | `200` |
| 플러스 3 | `231` / `233` / `236` | `23` / `32` | `311`, `2313` | `320` |
| 플러스 4 | `241` / `243` / `246` | `24` / `33` | `411`, `2413` | `500` |
| 플러스 5 | `251` / `253` / `256` | `25` / `34` | `511`, `2513` | `600` |

구형 베이직 선물은 `-1`(1개월·자동 결제), `13`(1개월), `1`(3개월), `2`(6개월), `3`(12개월)이고, 일반 구독은 `7`(1개월), `8`(3개월), `9`(6개월), 세리머니 일반 구독은 `1`(1개월), `2`(3개월), `3`(6개월)입니다. 이 표는 플레이어 코드 근거이며, 실방송에서 상품 의미까지 확인된 것은 현재 `0108 itemType=11`의 베이직 1개월 선물권, `0091 itemType=101`의 베이직 1개월 정기구독권, `0091 itemType=111`의 베이직 1개월 구독, `0091 itemType=103`의 베이직 3개월 정기구독권, `0091 itemType=9200`의 VOD 플러스 구독입니다. 상품표에 없는 값은 `subscriptionProduct=null`로 두고 원본을 보존합니다.
- `0121`: 도전미션 또는 대결미션 JSON. 공식 플레이어에서 도전미션은 `CHALLENGE_GIFT`, `CHALLENGE_NOTICE`, `CHALLENGE_SETTLE`, 대결미션은 접두사 없는 `GIFT`, `NOTICE`, `SETTLE`로 분기합니다. 이를 `missionKind`와 `action` 판별 유니온으로 노출하고 원본 객체도 보존합니다.
- 도전미션 `GIFT`는 `missionKey`, `uuid`, 후원자·방송인, chat number, relay 여부, 이미지, 제목과 후원 개수를 제공합니다. 화면의 개별 후원 문구에는 제목이 표시되지 않지만 패킷에는 들어 있습니다. `NOTICE`는 같은 `missionKey`의 제목과 `mission_status=SUCCESS|FAIL`, `SETTLE`은 제목과 `settle_count`를 전달합니다.
- 3시간 41분의 미션 집중 캡처에서 94개 `GIFT`, 85개 `NOTICE`, 78개 `SETTLE`을 관찰했습니다. 성공 78건은 모두 `SUCCESS → SETTLE → 0125`로 이어졌고, 실패 7건에는 정산이 없었습니다. 같은 사용자의 100+33+67개 후원은 동일 `missionKey`로 묶여 200개로 정산됐으며, 관찰한 모든 성공 미션에서 후원 합계와 `settle_count`가 일치했습니다.
- `missionKey`는 같은 미션의 여러 패킷에서 유지됩니다. `uuid`는 각 `0121` 알림마다 달랐지만 `CHALLENGE_SETTLE`과 이에 대응하는 `0125`는 같은 값을 사용하므로 두 정산 이벤트를 연결할 수 있습니다.
- `GIFT` 뒤 `NOTICE`가 없는 사례도 있습니다. 추가 캡처에서는 `CHALLENGE_GIFT` 수신 뒤 화면이 수락 대기 상태였다가 스트리머가 수락했지만, 수락 순간에 대응하는 채팅 WebSocket 패킷은 없었습니다. 따라서 `CHALLENGE_GIFT`는 제안·후원 수신을 뜻할 뿐 수락 완료를 뜻하지 않습니다. 대기·수락·거절을 별도 상태로 추측하지 않으며, 결과 패킷이 없다는 이유로 `rejected` 상태를 만들지 않습니다. 도전미션 후원은 같은 시각의 일반 별풍선 `0018`로 중복 전송되지 않았습니다.
- `0125`: 도전미션 정산 뒤 팬 상태를 전달하는 JSON입니다. `list`의 각 항목은 `[userId, nickname, contributionCount, becameFanClubFlag, becameTopFanFlag]`이며, `fanOrder`는 `becameFanClubFlag=1`인 경우에만 “N번째 팬클럽” 문구에 사용됩니다. 플래그가 0인 기존 팬에게 순번이 표시되지 않는 사례와, 플래그가 1일 때 3684번째·3689번째·7447번째 팬클럽 문구가 표시되는 사례를 확인했습니다. 6,850개 정산의 `fanOrder=3722`와 500개 정산의 `fanOrder=5098`도 참여자 팬클럽 플래그가 모두 0이었고 화면에 팬클럽 문구가 없었습니다. `chatNo`, `uuid`, 구조화한 참여자 목록과 원본 객체를 함께 보존합니다.

## OGQ 이모티콘

`0109`는 OGQ 이미지가 표시되는 채팅 이벤트입니다. 이미지 하나만 표시될 수도 있고 이미지와 텍스트가 함께 표시될 수도 있습니다. 플레이어 레이아웃은 다음과 같습니다.

```text
chatNo, message, groupId, subId, version,
senderId, senderNickname, senderFlag, BGR color,
chatLanguage, emoticonType, extension,
subscriptionMonth, nicknameColor, nicknameColorDark,
accumulatedSubscriptionMonth, representativePersonalconMonth,

```

장시간 캡처의 246건 중 242건은 이미지 전용이라 `message`가 빈 문자열이었고, 4건은 화면에서 이미지와 `message` 텍스트가 함께 표시됐습니다. 관찰된 `extension`은 `png`였습니다. BGR 정수 색상은 플레이어와 동일하게 CSS `#RRGGBB` 문자열로 변환합니다.

## 채팅창 얼음

추가 실방송 캡처에서 다음 순서를 확인했습니다.

```text
0005 chatMessage: 방송인이 !얼음 입력
0021 iceModeEx: [1, (플레이어가 무시), 528, 1, 1]
0019 iceMode: [1, 1, 528, (빈 필드)]
```

화면에는 “채팅창을 얼렸습니다.”가 표시됐고 이후 관찰된 일반 채팅은 모두 방송인 메시지였습니다. 이 문구는 별도 메시지 패킷이 아니라 플레이어가 `0021` 상태를 받아 생성합니다.

현재 플레이어의 `SVC_ICEMODE_EX` 분기는 첫 필드를 얼음 여부, 세 번째 필드를 허용 역할 비트마스크, 네 번째와 다섯 번째 필드를 별풍선·구독 제한 수치로 사용합니다. 역할 비트는 방송인 `16`, 팬클럽 `32`, 서포터 `64`, 열혈팬 `128`, 구독자 `256`, 매니저 `512`이며, 관찰값 `528`은 방송인과 매니저입니다. 두 번째 필드는 플레이어가 읽지 않으므로 이름을 붙이지 않습니다.

`0019 SVC_ICEMODE`는 enum과 실방송 패킷에는 존재하지만 현재 플레이어의 주 채팅 처리 분기가 없습니다. 해제 장면도 아직 실관찰하지 못했으므로 `0019`는 계속 원본 필드로만 제공하고, `0021`만 공식 분기에 맞춰 구조화합니다.

## 투표

`0050 SVC_NOTIFY_POLL`은 `[status, broadcasterId, pollNo, show]` 순서입니다. 같은 투표 번호의 실방송 화면과 대조해 `status=1`은 시작, `status=4`는 마감과 결과 공개, `status=2`와 `show=0`은 UI 제거로 확인했습니다. `status`와 `show` 원본을 보존하고 `pollState` 및 `visible`을 함께 제공합니다. 질문·선택지·득표수는 채팅 패킷에 없으므로 추측해 만들지 않습니다.

## 채팅금지와 강퇴

`0008 setDumb`는 채팅금지 대상, 지속 시간, 누적 횟수와 명령 주체를 전달합니다. 같은 사용자가 방송인에 의해 30초·1회 채팅금지를 받은 직후 매니저에게 다시 제재돼 60초·2회로 늘어난 사례와, 방송인이 서로 다른 두 사용자에게 각각 30초·1회 채팅금지를 적용한 화면을 패킷 및 별도 확인 경로와 대조했습니다. 공식 플레이어도 지속 시간을 초 단위로 사용하며 `commanderType=1`을 방송인, `2`를 매니저로 표시합니다. 플레이어가 무시하는 다섯 번째 필드는 실제 표본에서 명령 주체의 SOOP ID와 일치해 `commanderId`로 제공합니다.

`0012 setUserFlag`는 공식 플레이어와 같은 순서로 변경 후·변경 전 사용자 플래그를 제공합니다. 신규 팬클럽 별풍선 후원 12건에서는 `0018 becameFanClub=true` 직후 0~10ms 안에 `0012`가 이어졌고, 주 플래그에 `32`가 추가되며 보조 플래그는 유지됐습니다. 이에 따라 원본 문자열과 함께 변경 전후 `flag1`·`flag2`, `isFanClub`·`wasFanClub`을 제공합니다.

새 캡처의 애드벌룬 10개와 별풍선 50개·1개 후원은 모두 팬클럽 가입 문구 뒤 열혈팬 가입 문구가 표시됐습니다. `0087 isTopFan=true`와 `0018 topFanLevel=1`이 각각 열혈팬 문구에 일치했고, 뒤따른 `0012`도 팬클럽 비트 `32` 다음 열혈팬 비트 `32768`을 추가했습니다. `0018`은 원본 `topFanLevel`과 함께 정확히 `1`일 때 `becameTopFan=true`를 제공합니다. 다른 숫자의 화면 의미는 추측하지 않습니다.

공식 플레이어는 주 플래그 `2^17`을 `NODIRECT`로 정의합니다. `allowWhisper(false)`일 때 이 비트를 추가하고 `allowWhisper(true)`일 때 제거하므로, 공통 `UserStatus.isWhisperAllowed`는 비트가 없을 때 참입니다. 새 캡처의 `0012` 18건은 모두 이 비트가 추가되는 변경이었습니다.

공식 플레이어는 보조 플래그의 `2^18`, `2^19`, `2^20`을 각각 `FOLLOW_TIER1`, `FOLLOW_TIER2`, `FOLLOW_TIER3`으로 정의하고 이를 `isFollower`와 `getSubscriptionTier()` 판정에 사용합니다. 새 캡처에서는 같은 사용자의 세션 두 건 모두 `2^18`이 추가돼 비구독자에서 티어 1 구독자로 바뀌었고, 약 11.2초 뒤 `0091 itemType=111` 구독 세리머니가 이어졌습니다. 라이브러리는 이를 변경 전후 `isFollower`와 `followerTier`로 제공합니다. 함께 추가된 주 플래그 `2^28`은 공식 상수에 의미가 정의돼 있지 않으므로 원본으로만 보존합니다.

플레이어 `UserInfo` getter, `LiveView.js`의 사용자 플래그 판정과 공식 Chat SDK의 `userStatus`를 대조해, 원본 사용자 플래그가 있는 이벤트에는 공통 `UserStatus`를 제공합니다. BJ·매니저·열혈팬·팬·서포터·귓속말 수신 허용·구독자·게스트·퀵뷰·모바일·성별·A태그·운영 권한 비트를 각각 독립적으로 판정하며, 여러 비트를 하나의 역할이나 UI 표시 등급으로 축약하지 않습니다. 이벤트별 필드명과 전체 비트 표는 [이벤트 레퍼런스](events.md#사용자-상태)에 정리합니다.

다른 사용자의 강퇴는 별도 `0011`이 아니라 `0004 chatUser`의 퇴장 패킷으로 관찰됐습니다. 공식 플레이어는 `quitFlag === 1`만 일반 퇴장으로 처리하고 나머지를 `kickout`으로 전달합니다. 이번 캡처에는 `quitFlag=2`인 강퇴 6건이 있으며 라이브러리는 `isKicked: true`를 제공합니다. 함께 온 `etcInfo=1|2`의 의미는 플레이어도 해석하지 않으므로 원본으로 유지합니다.

- `0009 directChat`, `0023 slowMode`: 귓속말 양쪽 사용자와 운영자 여부, 자동·수동 슬로우모드 시간을 제공합니다.

- `0045 sendQuickView`: 공식 플레이어 분기대로 일반 퀵뷰 `1/2/3`을 `30/90/365`일, 퀵뷰 플러스 `100/101/102/103`을 `7/30/90/365`일로 구조화합니다. `itemType=100`은 실방송의 퀵뷰 플러스 7일 이용권 선물 화면과 대조했습니다. 추가 캡처에서 한 사용자가 보낸 `itemType=1` 20건은 각각 다른 수신자의 퀵뷰 30일 이용권 선물 화면과, 다른 사용자가 보낸 `itemType=101` 16건은 퀵뷰 플러스 30일 이용권 선물 화면과 일치했습니다. 전체 개수의 합계 패킷은 없으므로 수신자별 이벤트를 임의로 묶지 않습니다.
- `0047 itemUsing`: 공식 플레이어가 실제 사용하는 남은 초와 `Math.round(seconds / 60)` 분 값을 제공합니다. 읽기만 하고 사용하지 않는 앞선 두 필드는 이름을 추측하지 않습니다.
- `0070/0071 buyGoods`, `0074 notifyVr`, `0075 notifyMobBroadPause`: 상품 구매, VR 연결 정보, 모바일 송출 일시정지·재개 상태를 제공합니다.

- `0107 stationAdcon`: 실방송의 방송국 애드벌룬 2개·4개 화면과 `count=2/4`가 각각 일치했습니다. 공식 플레이어처럼 `senderNickname`, `count`, 원본 `title`을 분리해 제공하고 지역화된 화면 문구를 합성하지 않습니다.
- 기존 구조화 이벤트 중 `0005 chatMessage`에는 캐리지 리턴 제거와 색상·누적 구독·대표 퍼스널콘·응원팀을, `0091 followItem`에는 티어·언어·URL 보정을 추가했습니다. `0107 stationAdcon.chatNo`는 공식 플레이어와 같은 원본 문자열로 바로잡았습니다.
- `0121 mission`의 대결미션도 `GIFT`·`NOTICE`·`SETTLE`별 공식 필드를 제공하고, `0141 nightbotTimeout`은 사유 코드를 언어 중립 판별 값으로 함께 제공합니다.

필드 순서는 공식 플레이어에서 확인했습니다. 캡처에 존재하더라도 화면 동작까지 대조하지 않은 이벤트의 provenance는 `player`로 유지합니다.

반대로 `0006 setChannelName`, `0017 clubColor`, `0128 adminChuserExtend`, `0137 userLanguageSet`은 공식 switch에서도 바로 종료하며 필드를 읽지 않습니다. `0094 translationState`는 별도 처리 분기가 없습니다. 이런 이벤트와 enum에만 있고 처리 분기가 없는 이벤트는 `raw.fields`에 보존합니다. `0007 setBjStat`은 공식 플레이어가 무시하지만 실방송 관찰 근거로 첫 숫자만 보수적으로 제공합니다.

## 별풍선 관찰 검증

`0018`의 송신자 닉네임, 개수, 팬클럽 가입 순번을 실방송 화면과 대조했습니다. 100개 후원과 7409번째 팬클럽 가입이 각각 `count=100`, `fanOrder=7409`로 일치했고, 별도의 154개 및 10개 후원도 `count`와 일치했습니다. 플레이어가 사용하는 `senderLanguage`와 `urlModify`도 공개 데이터에 포함합니다. 실제 닉네임과 메시지는 테스트 fixture에 사용하지 않습니다.

## 공개 이름 규칙

- 이벤트 타입은 공식 채팅 enum의 `SVC_*` 상수명을 출발점으로 lower camel case로 정합니다.
- 필드는 공식 플레이어가 UI 계층에 전달하는 속성을 우선하고, 역할 중심의 일관된 영어 camel case로 정규화합니다.
- UI와 패킷을 대조해 의미가 확인된 값만 구체적으로 모델링합니다. 의미가 불명확하거나 플레이어가 무시하는 필드는 이름을 추측하지 않고 `raw.fields`에만 보존합니다.
- 실관찰 전에는 `player` 또는 `reference`, 화면까지 대조하면 `observed` provenance를 사용합니다.

## 인증 연결

### 로그인과 19금 방

성인 인증이 완료된 한 계정으로 이미 19금으로 설정된 서로 다른 두 실방송을 확인했습니다. 익명 라이브 정보 API는 두 방 모두 `RESULT=-6`만 반환하고 `REASON`은 없었지만, 로그인 뒤에는 `RESULT=1`과 채팅 서버 정보가 반환됐고 두 방 모두 실제 `0002` 입장 응답까지 받았습니다. 실제 계정 정보와 방송인 아이디는 기록하지 않습니다.

확인된 최소 순서는 다음과 같습니다.

1. `LoginAction.php`에 계정 정보를 전송하고 로그인 유지·아이디 저장 없이 `AuthTicket`을 받습니다.
2. 라이브 정보 API에 `AuthTicket` 쿠키를 보내 `TK`, `FTK`와 일반 `ChannelInfo` 필드를 받습니다.
3. `0001`에 `TK`를 넣은 `\f<TK>\f\f16\f`을 전송합니다.
4. 서버의 `0001` 뒤 `0002`에 `CHATNO`와 `FTK`를 넣은 `\f<CHATNO>\f<FTK>\f0\f\f\f`을 전송합니다.

공식 플레이어는 `0002`의 마지막 필드에 접속 로그와 `pwd`, `auth_info`, `pver`, `access_system` 값을 조합하지만, 두 실방송의 읽기 전용 입장에는 빈 값으로 충분했습니다. 라이브러리는 확인된 최소 필드만 보냅니다.

`createNodeChannelResolver`는 계정 정보를 받아 `AuthTicket`을 Node 프로세스 메모리에서만 재사용합니다. `TK`와 `FTK`도 `ChannelInfo`의 열거 필드나 이벤트에 넣지 않고 내부 `WeakMap`에 연결하므로 JSON 직렬화로 유출되지 않습니다.

서버 보조 브라우저 연결에서는 `authenticateNode`가 서버에 보관할 `AuthTicket`을 반환하고, `resolveNodeChannel`의 두 번째 인수에 이를 `authentication`으로 전달합니다. 이 호출은 직렬화 가능한 `AuthenticatedChannelInfo`에 `TK`와 `FTK`를 포함합니다. 브라우저 클라이언트는 두 값을 검증하고 내부 `WeakMap`으로 옮긴 뒤 위와 같은 인증 패킷을 보냅니다. `AuthTicket`은 브라우저에 전달하지 않습니다. 애플리케이션 서버를 무상태로 운영하려면 `AuthTicket`만 인증된 암호화 방식으로 봉인한 HttpOnly 쿠키를 사용하며, 계정 비밀번호나 평문·서명 전용 토큰은 쿠키에 저장하지 않습니다. 로그인 API 오류는 계정 정보나 응답 본문을 포함하지 않는 `AuthenticationError`로 전달합니다.

방송 중 19금이 적용된 실방송에서는 해당 시각에 전용 채팅 opcode나 소켓 재연결이 없었고, 이미 연결된 익명 채팅 WebSocket이 방송 종료까지 유지됐습니다. 정상 퇴장 증가와 이후 입장 급증은 관찰됐지만 접근 제한의 직접 신호가 아니므로 이벤트로 해석하지 않습니다. 현재 채널 리졸버는 최초 연결과 재연결 때만 제한을 판정하며, 연결 중 제한 변경을 감지하려면 별도의 라이브 정보 조회가 필요합니다.

### 비밀번호 방

라이브 정보의 `BPWD=Y`로 제한을 감지할 수 있습니다. 실제 입장에는 비밀번호 검증 단계와 인증된 `pwd` element가 필요합니다. 평문 비밀번호를 재연결 로그나 이벤트 원문에 남기지 않는 정책도 필요합니다.

### 구독플러스 방

플레이어의 접근 판정과 로그인 계정의 entitlement를 함께 재현해야 합니다. `EXPOSE_FLAG` 하나만으로 접근 권한을 추측하지 않으며, 실제 구독플러스 계정과 방의 입장 흐름은 아직 확인하지 않았습니다.

### 채팅 전송

전송은 인증된 입장 이후 `0005` 계열 payload를 사용합니다. 구현 전에 다음 항목을 확인해야 합니다.

- 서버가 요구하는 사용자 플래그와 세션 필드
- 메시지 길이·금칙어·도배 제한
- 채금, 강퇴, 슬로우 모드 오류 응답
- 전송 중 재연결됐을 때 중복 전송 방지
- 귓속말 `0009`와 일반 메시지의 권한 차이

이 조건이 검증되기 전에는 채팅 전송 메서드를 공개 API에 미리 추가하지 않습니다.
